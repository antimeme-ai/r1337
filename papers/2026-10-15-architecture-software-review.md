# Architecture review: local control, acquisition and remote boundaries

Review date: 2026-10-15. Scope: the first proposed `docs/ARCHITECTURE.md` and `docs/CAPABILITIES.md`, specifically host/supervisor/engine responsibilities and device-action failure behavior. Section names and line references below refer to the draft read for this review. Read current agent guidance, shared doctrine, project brief, latest journal entries, the research synthesis and the relevant portable-system, Flipper One, analog/control and BP5 reports. No new external research, implementation, device operation or dependency selection occurred. Only this report was edited.

The split between local timing, host presentation/storage and remote analysis is suitable for further design. The draft already distinguishes native samples from interpretations, clock domains from host timestamps, target-changing actions from analysis retries, and electrical adapters from device semantics. Four omissions need resolution before a prototype plan relies on those boundaries. None requires selecting a processor, runtime, protocol framework or generalized orchestration system.

## F1 — High: autonomous output behavior after host failure is undefined

**Affected sections:** [Functional boundaries](../docs/ARCHITECTURE.md#functional-boundaries), especially the supervisor and engine rows (draft lines 76–84); [Power, noise and operating modes](../docs/ARCHITECTURE.md#power-noise-and-operating-modes), lines 161–175. Relevant matrix entries: electrical waveform stimulus, vector/scalar network response, optical stimulus and wired device access.

**Practical failure:** the host configures a waveform or target-power output, then hangs or shuts down while the engine remains powered and running. Independent waveform/transaction execution is intentional, but the draft assigns only host shutdown/power sequencing to the supervisor. It gives neither the engine nor an independent control path responsibility for what happens to the configured output. Pressing the instrument power button could therefore blank the UI while leaving a driven target or RF stimulus active. Conversely, indiscriminately removing engine or target power could interrupt a firmware operation. A local timing boundary does not itself choose the correct behavior in either case.

**Proposed resolution:** add a short output/failure contract to the architecture. Each output-capable engine/profile must define its behavior on host-link loss, host restart, requested shutdown and relevant power failure: finish a bounded operation, stop, hold a defined state or require operator intervention, as appropriate to that operation. Say which component can enact the behavior, whether its path remains available without a functioning host, and what remains unknown if it cannot confirm completion. Describe operator stop and power-off separately; neither should implicitly promise reversible cancellation of a dispatched target action. Do not prescribe one global “all outputs off” policy or add an independent stop circuit before the actual engine paths establish what is possible. Unsupported cases can be explicitly excluded from unattended use.

## F2 — Medium: retained captures and recording indication have no completeness contract

**Affected sections:** [Physical architecture](../docs/ARCHITECTURE.md#physical-architecture), lines 133–137; [Timing, storage and remote support](../docs/ARCHITECTURE.md#timing-storage-and-remote-support), lines 184–201; capability rows “Digital observation” and “Voice field notes.”

**Practical failure:** an engine completes acquisition into a finite buffer, but host retrieval fails; alternatively the host receives a stream until storage fills or samples overrun. A recording indicator could continue to reflect a requested capture rather than accepted recording, and an existing session file could look like a complete result. “Retain originals” and adequate nominal bandwidth do not distinguish these states. The existing portable-system report already identifies the need for explicit overrun/incomplete-capture reporting; the architecture does not carry that requirement forward.

**Proposed resolution:** require each capture result to distinguish a complete capture, a known retained portion with gaps/truncation, and an unavailable/unknown remainder. Preserve the actual settings and engine continuity/reset information with the portion that exists; never silently relabel it as a complete acquisition or silently overwrite the only buffered copy. Assign engine-side overflow/status reporting to the engine adapter and host-side storage failure/reporting to the host. Define recording indication in terms of acknowledged recording state, with a visible failure/unknown state when confirmation is lost; a supervisor that cannot observe storage must not imply that data is being retained. Exact buffering strategy, timeout values, durability guarantees and file layout belong to the later capture design.

## F3 — Medium: configuration ownership does not cover competing controls or endpoint changes

**Affected sections:** [Functional boundaries](../docs/ARCHITECTURE.md#functional-boundaries), lines 75–79; [Capability coverage and stash assignments](../docs/ARCHITECTURE.md#capability-coverage-and-stash-assignments), BP5 and Flipper roles; [Heterogeneous control systems](../docs/ARCHITECTURE.md#heterogeneous-control-systems), lines 221–226. Matrix entries include wired access, waveform stimulus and visible inspection/client roles.

**Practical failure:** the host nominally owns configuration, yet the proposed system also retains native board controls and can expose a phone client. Two control surfaces can change a shared range, drive state or instrument mode while a capture/action is pending. A disconnected USB instrument may return in a reset mode, or a different target can be attached while a prepared operation still names an old profile. The host can then record the intended settings rather than those used, or send an action under stale electrical/profile assumptions. The draft acknowledges resource conflicts but does not assign responsibility for preventing this class of conflict.

**Proposed resolution:** state that one local host operation owns configuration and actions for each affected physical interface/output during that operation. Other clients submit requests through that owner; native controls must either participate in that agreement or invalidate the host's configuration knowledge. Bind execution and capture metadata to the identified engine, applied configuration and equipment/profile context. Disconnect, reset, an unaccounted native change or a reported target/adapter change invalidates prepared actions until the relevant state is checked again. This does not require automatic physical target identification or a distributed lock service. A simple local ownership rule and explicit operator-confirmed connection context can meet the architectural need.

## F4 — Medium: unknown-outcome reconciliation assumes an observable device state

**Affected section:** [Timing, storage and remote support](../docs/ARCHITECTURE.md#timing-storage-and-remote-support), lines 203–210, especially “reconcile it with the device before issuing another operation”; [Heterogeneous control systems](../docs/ARCHITECTURE.md#heterogeneous-control-systems), workflow completion/failure conditions. Matrix row “Remote support and records.”

**Practical failure:** a legacy controller accepts a write-only command and its acknowledgment is lost. There may be no query that establishes whether it took effect. The draft's absolute requirement either leaves the workflow permanently blocked or pressures an implementation to invent reconciliation. It also appears to prohibit a documented diagnostic or stop operation because that is “another operation,” even when it is the appropriate response to uncertainty. Timeouts and reconnects cannot resolve that semantic gap by themselves.

**Proposed resolution:** make reconciliation operation/profile-specific. Record the dispatched action and unknown result; prohibit automatic repetition or state-dependent continuation that assumes success/failure. Permit documented observations or recovery/stop actions that are valid under the remaining uncertainty. Where device state cannot be established, retain the unknown outcome and require the defined operator recovery/re-identification step before resuming dependent work. Cancellation means a requested action may already have happened; sending a stop is its own operation with its own result. This narrows the existing no-silent-replay rule without adding a general workflow engine.

## Deliberately not findings

Remote support already has a bounded reference/analysis role; the draft does not promise remote hardware timing or authorize arbitrary model-generated commands. Source/uncertainty retention is present. No additional remote-control stack is needed to correct these findings. The detailed binary record format, job-transfer protocol, persistence implementation, authentication mechanisms, test framework and library/runtime choices remain outside this first architecture review.

The next design revision can resolve the findings with ownership and failure-behavior statements. A later concrete prototype plan can test them directly through host/process loss during active output, buffer/storage failure, competing configuration requests or reconnect, and lost action acknowledgments. Those are distinct failure classes, not a request for implementation or tests in this documentation phase.

## Revision assessment — 2026-10-15

Reread the revised architecture and capability matrix after root integrated review findings. **F1–F4 are addressed at the maturity of this first architecture; no requirement from this review remains missing.** The initial findings above are retained as review history.

- **F1:** “Power, noise and operating modes” now requires operation-specific output behavior through link loss, restart, standby, shutdown, low energy and power restoration, names the enforcing engine/independent path, distinguishes stop from power-off, and requires actual output/target-power indication when state outlives the UI. It expressly avoids assuming supervisor control over unconnected engines or electrical disconnection when unpowered. Selection and verification of each real engine's behavior remain later design work.
- **F2:** “Timing, storage and remote support” now distinguishes bounded capture, streams and decoded events; requires complete/partial/unknown results, actual settings and continuity information, explicit overflow/retrieval/storage failure, defined full-buffer behavior and acknowledged recording indication. Buffer sizes, storage durability and file representation remain appropriately open.
- **F3:** “Functional boundaries” now assigns one local operation ownership of affected interfaces/outputs, routes phone/remote requests through it, handles native-control changes, binds actions/metadata to the actual configuration and connection context, and invalidates dependent prepared actions after disconnect/reset/unaccounted changes.
- **F4:** “Timing, storage and remote support” now preserves unknown outcomes without automatic replay or assumed dependent continuation, permits documented observations/stop/recovery valid under uncertainty, and defines operator recovery/re-identification where device state cannot be established.

The capability matrix explicitly applies these contracts across its rows. The unchanged high-level diagram is acceptable because the prose now states that engine-specific enforcement paths still need design and that supervisor-to-engine control is not implied. This assessment confirms architectural requirements, not implementation or tested reliability; the later prototype plan must map them to the selected hardware and exercise the distinct failure cases already identified.
