# Flipper One frumentarii — 2026-10-15

Flipper One is a close design reference for porter_ricks: a finished portable computer that integrates a low-power control processor, Linux compute, network interfaces, internal expansion, physical controls, power management and antenna mechanics. Its strongest lessons concern making those components behave like one object. It does **not** establish a finished universal RF/debug instrument, an arbitrary-I/Q Wi-Fi radio, or a complete industrial electrical interface.

This pass read the [official Developer Portal](https://docs.flipper.net/one), pinned its documentation and MCU source, and inspected the published hardware and mechanical repositories. Four original archives were preserved; [the lane acquisition manifest](2026-10-15-flipper-one-acquisitions.md) records revisions, hashes, restoration commands and publication limits. No acquired code was executed, installed or built; no device was operated. All performance measurements below remain the developers' reports, not our reproductions.

## What exists, and what remains a development claim

The portal describes an actively developed, community-driven portable Linux platform. The evidence has several distinct levels:

| Evidence | What it supports | What it does not establish |
| --- | --- | --- |
| Published MCU source with board targets, drivers, input/display/power services and interprocessor code | Concrete implementation can be studied | That every path works or meets timing/power requirements |
| Prototype photos, dev logs and build-specific test transcripts | Hardware prototypes and reported observations exist | Production qualification or general reliability |
| External STEP models, back plate/antenna rail and selected public Altium designs | Concrete mechanical integration and some electrical designs are open for study | A complete reproducible product design |
| Lists of SDR, satellite, accelerator and other expansion categories | Intended extension space | A compatibility matrix of tested modules |
| FlipCTL/profile/atomic-update discussions | UI and software-management direction, with some prototypes | All advertised frontends, plugins and update guarantees already working |

The official source map includes [Linux image assembly](https://github.com/flipperdevices/flipperone-linux-build-scripts/tree/9606c32f91a7798a97e88ea87acffff5b4c80892), [kernel patches/configuration](https://github.com/flipperdevices/flipper-linux-kernel/tree/d66a9f4f3efa5f14df5db733ef77f8abe68c371a), [U-Boot](https://github.com/flipperdevices/u-boot/tree/9337c09e4c9ba5b1641a003abd157a6b3e8caf8d), [board testing](https://github.com/flipperdevices/flipperone-testing/tree/2298fb5b3548dde68cce536e15ecfe1d163c4bd7), and the MCU implementation examined below. The image assembler distinguishes upstream-oriented and vendor-BSP builds and explicitly requires Rockchip DDR-initialization/Maskrom-loader binaries. Those repositories were located and their overview read, without acquiring their complete dependency trees or auditing the kernel.

The [hardware repository at the acquired revision](https://github.com/flipperdevices/flipperone-hardware/tree/f6f21591643226aa86727a9a637e618b10faf158) contains a README and images, not mainboard design files. Its README points to the [public Altium space](https://flipper.365.altium.com/designs/folder-A78C8D02-EA07-49E1-AC7A-E84FAA2AF410), explicitly saying that designs absent there are not open. I did not acquire a complete mainboard schematic/BOM from that viewer. The [mechanics repository](https://github.com/flipperdevices/flipperone-mechanics/tree/8d90ad86b3ed2e83e5cf20c538233c9a09dadb8f) intentionally simplifies the public main body to an external shell; the back plate and antenna rail expose their internal geometry. “Open development” is meaningful here, but publication scope differs by component.

## A coherent processor split

The [published specification](https://docs.flipper.net/one/general/tech-specs) describes RK3576 application compute, 8 GB LPDDR5 and 64 GB UFS, alongside an RP2350B MCU. Its display is 256 × 144 with 64 grayscale levels; Ethernet is two gigabit ports. Three USB connectors have distinct host/data/power roles. Size is listed as 155 × 67 × 40 mm; weight is pending. These are development specifications rather than final shipping guarantees. The RP2350's alternative Arm/RISC-V cores should not be read as four simultaneously executing cores.

According to [MCU architecture](https://docs.flipper.net/one/mcu-firmware/architecture), Linux owns the high-level USB, HDMI, M.2, Wi-Fi, Ethernet and audio environment. The MCU owns display output, buttons/touchpad, haptics, LEDs, power/battery, USB-C CC negotiation and CPU boot control. The [interconnect](https://docs.flipper.net/one/mcu-firmware/mcu-cpu-interconnect) separates UART console, SPI framebuffer, I²C commands/input events, interrupt notification and boot-control GPIO. These are concrete functional channels, not one unrestricted “smart coprocessor” link.

The acquired MCU implementation grounds that description. [`targets/f1/src/main.c`](https://github.com/flipperdevices/flipperone-mcu-firmware/blob/93d73772144451b582d0ebbd5af61db41e40145e/targets/f1/src/main.c) initializes Furi, starts initialization and then the scheduler. [`applications/services/i2c_intercom/i2c_registers_map.h`](https://github.com/flipperdevices/flipperone-mcu-firmware/blob/93d73772144451b582d0ebbd5af61db41e40145e/applications/services/i2c_intercom/i2c_registers_map.h) defines versioned registers, input states, interrupt masks, read-to-clear behavior, lighting and haptics. Persistent brightness settings and ephemeral input events have different semantics.

[`applications/main/cpu/cpu_app.c`](https://github.com/flipperdevices/flipperone-mcu-firmware/blob/93d73772144451b582d0ebbd5af61db41e40145e/applications/main/cpu/cpu_app.c) receives Linux frames and hands them to the GUI; its ISR reports failure when the application queue cannot accept another frame. [`lib/drivers/pio_get_frame/pio_get_frame.c`](https://github.com/flipperdevices/flipperone-mcu-firmware/blob/93d73772144451b582d0ebbd5af61db41e40145e/lib/drivers/pio_get_frame/pio_get_frame.c) uses PIO/DMA and two buffers sized at width × height. This is a real implementation seam worth studying, without claiming we audited frame ownership or demonstrated its limits.

**Lesson for porter_ricks:** keeping power controls, essential status, recovery entry and time-sensitive acquisition available independently of Linux is a strong candidate pattern. It does not require copying this processor pair or putting every measurement through that MCU. A high-bandwidth RF stream and a low-rate control/status link should have explicitly different paths. The proposed remote support station belongs above the locally functioning instrument, not inside its timing loop.

## RF capability is a path through the system

Flipper One's [M.2 interface](https://docs.flipper.net/one/hardware/m2-port) is Key B with PCIe 2.1 ×1, USB 2/3, SATA, serial/control and SIM-related signals. Mechanical size and single-sided thickness limits are explicit. The [module guide](https://docs.flipper.net/one/hardware/m2-port/modules) now calls out real incompatibilities: sSDR Rev3's Key M does not fit; older B+M Rev2 fits mechanically but its PCIe ×2-to-×1 behavior is unconfirmed. ESP32-E22 is also not on their confirmed list because key/interface fit is unresolved. These cautions qualify earlier broad “universal module” descriptions.

For our instrument, that is the useful lesson: connector fit, transport, lane count, peak power, driver, sustained data rate, antenna routing and enclosure clearance form one capability. A slot full of interface names is not yet usable SDR coverage. A single slot also forces tradeoffs if SDR, extra storage, cellular and acceleration each want it; alternatives must be explicit rather than counted simultaneously.

The [Wi-Fi hardware page](https://docs.flipper.net/one/hardware/wifi-bluetooth) identifies the MT7921AUN module and describes a particularly concrete integration trick. Its SuperSpeed connection can operate independently of the USB 2 wires on the chosen hub branch, allowing those USB 2 wires to serve the expansion header. MCU-controlled power and reset sequencing are required for correct module initialization. This demonstrates resource-aware integration, not free extra bus bandwidth. Source and topology still have to establish which other loads share upstream bandwidth.

The [monitor-mode test page](https://docs.flipper.net/one/testing/network/wifi/monitor) records a build-1350 Debian test on June 23, 2026, including captured 5 GHz beacon output. That is stronger than a bare support assertion, but its shown transcript does not establish every advertised band, simultaneous role, loss rate, or arbitrary I/Q samples. Their built-in Wi-Fi and prospective SDR modules remain different capabilities.

**Lesson for porter_ricks:** preserve the actual observation type—packet, demodulated timing, digitized voltage, or complex RF samples—through the product UI and capture metadata. Capability breadth should come from complementary paths with known limits. A USB/shared-memory/PCIe export budget and local buffering are design inputs even if heavy analysis happens remotely.

## Power and heat are product behavior

The [power subsystem](https://docs.flipper.net/one/hardware/power-subsystem) describes a two-cell battery and individually controlled converters/switches. Its preliminary figures include 22.9 Wh battery energy, 60 W USB-C input and a 13 W M.2 output allowance, with thermal derating explicitly possible. The broader specification still lists approximately 24 Wh and a nonfinal capacity figure. Those discrepancies are development state, not values to combine into a precise runtime estimate. Prototype-only instrumentation includes additional domain-level current monitors beyond the production-oriented total-power monitor/fuel gauge.

The [heatsink page](https://docs.flipper.net/one/mechanics/heatsink) treats aluminum as both thermal and structural hardware. It reports preliminary testing/simulation at 21 °C ambient, around 6 W thermal load and heatsink temperature below 50 °C under selected realistic loads. Higher load or ambient temperature can reduce clocks, charging and peripheral power. Those conditions bound the claim; they do not demonstrate the same temperatures with a high-power SDR installed.

**Lesson for porter_ricks:** simultaneous-use states need budgets: RF acquisition plus storage plus display plus charging is different from idle networking. The polished object should reveal power limits and retained capability coherently. A port current limit is not a promise that every output can supply its maximum at once. Antenna placement and thermal paths should be part of enclosure development from the beginning.

## Camera, basic sensors and control-system access

The official [GPIO-module page](https://docs.flipper.net/one/hardware/gpio-port/modules) describes its camera as an ordinary USB webcam using header USB 2 data and 5 V power, with a grayscale preview on the local display. This is a clean software boundary: camera transport enters Linux through a standard device interface; presentation need not determine the retained original image. The same page presents an SA828-based radio/audio/PTT module as an expansion example, rather than claiming that RF hardware is built into the base device.

The [GPIO port](https://docs.flipper.net/one/hardware/gpio-port) exposes MCU/CPU pins with PIO, ADC and multiplexed digital functions plus protected power rails and USB data. These are building blocks, not a complete oscilloscope, programmer, CAN physical layer, isolated industrial input or safe interface for four decades of lab equipment. No measured analog bandwidth, precision front end or universal voltage adaptation follows from “ADC” or a CAN pin function.

**Lesson for porter_ricks:** camera and basic sensors can earn compact internal or single-companion roles without driving the main RF architecture. Lab control requires an additional separation between electrical adaptation, transport, device command semantics and coordinated action. A remote library can help identify all four; it cannot make an unidentified connector electrically safe or a guessed command correct.

## UI polish comes from ownership of the interaction

The [FlipCTL portal concept](https://docs.flipper.net/one/cpu-software/flipctl) emphasizes directional navigation and tool/service adapters behind a consistent UI, but its HTML/JavaScript and WebKit description lags current source. The current [image-build README](https://github.com/flipperdevices/flipperone-linux-build-scripts/blob/9606c32f91a7798a97e88ea87acffff5b4c80892/README.md) builds [flipctl-slint](https://github.com/flipperdevices/flipctl-slint/tree/88cb743d78b6cf3de846a1729e7735293b6d1238). That implementation describes an early Rust/Slint shared component library, DRM panel output, evdev controls, browser frame/input transport and an optional TUI sharing view models. Its README identifies Phase 0/1 work rather than a finished universal HMI. The [UI/design repository](https://github.com/flipperdevices/flipperone-ui/tree/d9029a19ef82cb15a9624ec01ec69e5780740483) is itself an overview/images tree pointing to Figma design resources. These are distinct artifacts. The useful lesson is common interaction/data across local and remote presentation; neither the old renderer nor the current framework is selected for porter_ricks.

The [mechanical mounting system](https://docs.flipper.net/one/mechanics/module-mounting-system) makes internal expansion serviceable while giving external modules screws and fitted covers. A separate antenna rail lets pigtails be routed before final closure. [Dev log 8](https://docs.flipper.net/one/dev-log/8) gives unusually practical polish evidence: cable channels, less stressed snap fits, visible Ethernet LEDs, a raised app-switcher button, and an audio jack moved outward after plugs failed to seat. These are concrete prototype feedback loops; an attractive render alone would not disclose them.

The acquired mechanical tree includes `CURRENT/B.1/Flipper One (B.1).stp` and artwork. It is a useful dimensional/accessory reference, not a fully open internal manufacturing model. For porter_ricks, the valuable pattern is an integrated exterior with considered status, controls, cables and service access. It can inform the folding tablet/cyberdeck brief without copying Flipper One's small monochrome screen or expanding into many carried modules.

## Software maintainability and recovery remain active engineering

The [mainlining report](https://docs.flipper.net/one/cpu-software/rk3576-mainlining) explains why the team wants a current upstream Linux/U-Boot/TF-A stack rather than permanent dependence on an old vendor BSP. It also lists remaining gaps including NPU, video encoding, CSI camera and PCIe suspend, with OP-TEE support absent. The release's accelerator TOPS figure is therefore not evidence of an available open inference stack. Required DDR initialization binaries and other boot components need separate treatment; “Linux is open” does not settle the entire startup chain.

The [Flipper OS concept](https://docs.flipper.net/one/cpu-software/flipper-os) separates a base system from user profiles and explicitly says reliable atomic-update mechanisms are still being explored. [Dev log 9](https://docs.flipper.net/one/dev-log/9) reports an installer and a newer Linux/initramfs Falcon boot menu, replacing the older U-Boot menu description. Its reported menu-start improvement from 3.9 to 2.8 seconds is a development measurement. This newer material qualifies older static UI pages; dates and actual source revisions matter.

**Lesson for porter_ricks:** capability adapters and restoreable known configurations can prevent a many-tool system from becoming an unrepeatable collection of modified utilities. Remote assistance should return reusable analysis and source references, with state-changing operations distinguished from retryable reads. Whether profiles, processes or another owned mechanism express that boundary remains a design question. We should study concrete failure semantics before promising automatic recovery or atomic updates.

## What to carry into design discussion

The strongest transferable ideas are independent local control, separated high-rate data paths, measured power states, mechanically resolved expansion, common UI semantics and maintainable software boundaries. The largest gaps relative to our brief are the actual RF front ends and capture ranges, precision/electrical protection, time-correlated heterogeneous measurements and device-specific firmware/control interfaces. Flipper One is valuable because its public work shows both integration and unfinished edges. It is a reference to learn from, not an architecture, purchase, dependency or implementation selected for porter_ricks.
